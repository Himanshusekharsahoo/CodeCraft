# CodeCraft — Developer Architecture Map & System Guide

An architectural overview of the CodeCraft cloud IDE platform. This document explains how subsystems interact, where code lives, and how data moves through the application.

---

## 2. `src/` Architecture Map

- **`src/app/`**: Next.js App Router root containing public pages (`login`, `register`, `profile`), authenticated user dashboard (`dashboard`), the collaborative workspace IDE (`workspace/[workspaceId]`), E2E test harness (`e2e-test`), and all backend API handlers (`app/api/`).
- **`src/components/`**: React UI components including the collaborative Monaco editor (`Editor.jsx`), multi-file sidebar (`Navpanel.jsx`), live presence overlay (`LiveCursor.jsx`), sandbox output terminal (`Output.jsx`), chat panel (`Chat.jsx`), Git control panel (`GitPanel.jsx`), and AI agent drawer (`AgentPanel.jsx`). The `ui/` subdirectory houses reusable Radix/Chakra primitives.
- **`src/config/`**: Contains `firebase.js`, the unified client-side Firebase SDK configuration initializing Auth, Firestore (`db`), and Realtime Database (`rtdb`).
- **`src/context/`**: Contains `AuthProvider.js`, providing application-wide React authentication state, active Firebase user profile, and automatic ID token refreshes.
- **`src/helpers/`**: Client-side authentication wrappers (`loginHelp.js`, `logoutHelp.js`, `signUpHelp.js`) orchestrating Firebase Auth credential exchange and Firestore `users` profile creation.
- **`src/lib/`**: Core backend business logic divided into isolated domains (`execution/`, `git/`, `ai/`), shared security helpers (`serverAuth.js`, `authEnv.js`), observability taxonomy (`observability.js`), error marker diagnostics (`diagnostics.js`), and workspace utilities (`workspaceHelpers.js`).

## 4. Authentication & Authorization Flow

```
Browser Client
   │
   ├─► Firebase Client SDK: signInWithEmailAndPassword() / signInWithPopup()
   │   └─► Receives Firebase JWT ID Token (valid 1 hour)
   │
   ▼
Next.js API Request (Authorization: Bearer <ID_TOKEN>)
   │
   ├─► serverAuth.js: verifyAuthToken()
   │   └─► Verifies token authenticity via Google Identity Toolkit REST API
   │
   ├─► executionAuth.js / gitAuth.js: fetchFirestoreWorkspaceMemberRole()
   │   └─► Checks Firestore REST: workspaces/{id}/members/{uid}
   │       └─► If absent: checks workspaces/{id} (ownerId === uid? or isPublic?)
   │
   ▼
Role-Based Access Control (RBAC) Enforcement
```

### RBAC Authority Matrix
- **`owner`**: Full administrative rights. Can edit files, run code, invoke AI agent, perform Git mutations, invite members, and delete workspace.
- **`contributor`**: Collaborative developer. Can edit files, run code, invoke AI agent, and perform Git operations (`commit`, `branch`, `merge`). Cannot invite members or delete workspace.
- **`viewer`**: Read-only guest. Can view files, inspect Git history/diffs, and view execution output. **Strictly forbidden** from executing code (HTTP 403), modifying Git state (HTTP 403), or mutating files via WebSocket.

---

## 5. Workspace Lifecycle Flow

1. **Creation**: User creates workspace on `/dashboard`. The frontend validates the name via `validateWorkspaceName()` and writes a document to `workspaces/{workspaceId}` in Firestore with `ownerId: uid`.
2. **Membership**: The owner invites collaborators via `POST /api/workspace/[workspaceId]/invites`. Invitations are appended to the recipient's `users/{uid}.invites` array. Upon acceptance, a record is added to `workspaces/{workspaceId}/members/{recipientUid}` with role `contributor`.
3. **Opening Workspace**: Navigating to `/workspace/[workspaceId]` mounts `workspace/[workspaceId]/page.jsx`, which verifies membership and retrieves the file hierarchy from `workspaces/{workspaceId}/files`.
4. **Editor Initialization**: Active files open in tabs in `Editor.jsx`. The client initializes a `Y.Doc` and establishes a WebSocket connection to the collaboration server.

## 6. Real-Time Collaboration Flow (Yjs)

```
Monaco Editor (Client A)
   │
   ├─► MonacoBinding ──► Y.Text (In-Memory CRDT)
   │                       │
   │                       ▼
   │                WebsocketProvider (y-websocket)
   │                       │
   ▼                       ▼
WebSocket Connection (ws://collab:1234/ws?room=workspace:{wsId}:file:{fileId}&token=...)
   │
   ├─► collaborationserver/src/rooms.js
   │   ├─► Authenticates token & verifies role via Firestore REST API
   │   ├─► Rejects write messages if role === "viewer"
   │   ├─► Applies update to shared room Y.Doc
   │   └─► Broadcasts binary update delta to peer WebSocket clients
   │
   └─► collaborationserver/src/persistence.js
       ├─► scheduleSave(workspaceId, fileId, content)
       ├─► Enforces 3.5s quiet period (max 10s continuous typing ceiling)
       └─► Writes snapshot to Cloud Firestore (PATCH .../workspaces/{id}/files/{fileId})
```

- **Room Naming**: Formatted as `workspace:{workspaceId}:file:{fileId}` ensuring strict multi-file data isolation.
- **Room Eviction**: When the last client disconnects from a room, debounced saves are flushed and the in-memory room `Y.Doc` is destroyed to prevent memory leaks.
- **External Mutations**: When Git or AI modifies files on disk, `firestoreSync.notifyCollabMutation()` dispatches `POST /notify-mutation` to the collaboration server to live-patch open editor sessions without a browser refresh.

## 7. Code Execution Flow (Docker Sandbox)

```
Browser Output Terminal
   │
   ▼
POST /api/workspace/[workspaceId]/execute
   │
   ├─► executionAuth.js: authenticateAndAuthorizeExecution() (Blocks Viewers with 403)
   ├─► rateLimiter.js: acquireExecutionSlot() (Max 2 concurrent runs, 20 req/min per user)
   ├─► dockerDetector.js: checkDockerAvailability() (Fails closed with 503 if daemon is offline)
   │
   ▼
ExecutionService.execute()
   │
   ▼
SandboxExecutor.execute()
   │
   ├─► Provisions unique scratch folder: data/executions/{executionId} (mode 0o775)
   ├─► Writes source files to disk
   ├─► Resolves language & container image from RuntimeRegistry
   │
   ▼
Docker Container Spawn
   ├── --network none                  (Zero outbound network access)
   ├── --memory 256m                   (Strict 256MB RAM limit)
   ├── --cpus 1.0                      (1.0 CPU quota)
   ├── --pids-limit 64                 (Fork bomb prevention)
   ├── --read-only                     (Read-only root filesystem)
   ├── --user 1000:1000                (Dynamic non-root execution)
   ├── --security-opt no-new-privileges (Privilege escalation blocked)
   └── Timeout: 10,000ms               (Kills hung execution; SIGKILL after 2s)
   │
   ▼
Structured Result returned: { stdout, stderr, exitCode, status, durationMs }
Scratch directory and container destroyed.
```
> [!NOTE]
> **Piston Execution Provider Removed**: CodeCraft executes code exclusively inside isolated Docker containers. Client-supplied commands, custom images, and remote Piston fallbacks are strictly prohibited.

## 9. Git Version Control & Firestore Sync

CodeCraft maintains a dual-layer storage model:
1. **Firestore Database**: Serves as the source-of-truth for collaborative editing, active file lists, and UI state.
2. **On-Disk Git Repository (`data/git/{workspaceId}`)**: Provides real Git branch history, diff computation, and commit tracking.

### Synchronization Bridge (`src/lib/git/firestoreSync.js`)
- **`syncFirestoreToWorkingTree(workspaceId)`**: Flushes pending Yjs collaboration server buffers to Firestore, then pulls files from Firestore into the local Git directory before Git commands (`status`, `diff`, `commit`) execute.
- **`syncWorkingTreeToFirestore(workspaceId)`**: When a Git branch is checked out or a commit is restored, this synchronizes files from the Git directory back to Firestore and calls `notifyCollabMutation()` so active Monaco editor tabs update instantly.

## 10. Firebase Architecture Map

- **Firebase Authentication**: Client user authentication (Email/Password and Google OAuth). Generates ID tokens passed via `Authorization: Bearer <token>` to Next.js API routes.
- **Cloud Firestore**: Primary persistent datastore:
  - `workspaces/{workspaceId}`: Metadata, owner ID, public visibility.
  - `workspaces/{workspaceId}/members/{userId}`: Workspace roles (`owner`, `contributor`, `viewer`).
  - `workspaces/{workspaceId}/files/{fileId}`: File metadata, paths, and content snapshots.
  - `users/{userId}`: User profiles, theme preferences, and pending invitations.
- **Realtime Database (RTDB)**: Used strictly for lightweight ephemeral collaborative presence and live cursor tracking (`LiveCursor.jsx`) with automatic disconnect cleanups (`onDisconnect().remove()`).
- **Server-Side Firestore REST Access**: Backend services (`executionAuth.js`, `collaborationserver/src/persistence.js`) query Firestore via Google REST endpoints passing the caller's Firebase ID token. This enforces `firestore.rules` under the user's verified identity without requiring admin service accounts.

## 13. Security Boundaries

1. **Authentication**: All mutation and execution routes require a valid Firebase ID token; test tokens are rejected when `NODE_ENV === "production"`.
2. **Authorization & RBAC**: Every request verifies workspace membership. Viewers are blocked from code execution, Git mutations, and document modifications.
3. **Execution Isolation**: Docker containers execute code with `read-only` rootfs, `--network none`, `--user 1000:1000`, 256MB RAM cap, and 10s timeouts. No host fallback exists.
4. **Path Traversal Guards**: Filenames and workspace IDs are validated against directory traversal (`..`, `\`, `/`, null bytes).
5. **Secret Scrubbing**: All logs, model prompts, and AI outputs are scrubbed of API keys, Bearer tokens, and private certificates.
6. **Internal Bridge Authentication**: Endpoints on the collaboration server require `x-collab-internal-token` matching `COLLAB_INTERNAL_SECRET`.

## 15. Request Lifecycle Examples

### A. User Login Flow
`src/app/login/page.jsx` (User submits form)
→ `loginWithEmailAndPassword()` in `src/helpers/loginHelp.js`
→ `signInWithEmailAndPassword(auth, email, password)` in Firebase Auth SDK
→ Firestore `users/{uid}` updated with `lastLogin` timestamp
→ `AuthProvider.js` emits state change
→ Next.js router navigates to `/dashboard`.

### B. Open Workspace Flow
`src/app/dashboard/page.jsx` (User clicks workspace card)
→ Router pushes `/workspace/[workspaceId]`
→ `src/app/workspace/[workspaceId]/page.jsx` mounts
→ Firestore listener watches `workspaces/{workspaceId}/members/{currentUser.uid}`
→ Normalizes role to `userRole` (`owner` / `contributor` / `viewer`)
→ Fetches initial files from `workspaces/{workspaceId}/files`
→ Mounts `<Editor workspaceId={...} userRole={...} activeFile={...} />`.

### C. Collaborative File Editing Flow
User types in Monaco editor
→ `MonacoBinding` in `src/components/Editor.jsx` updates local `Y.Text`
→ `WebsocketProvider` encodes and transmits binary CRDT update
→ `collaborationserver/src/rooms.js` receives update and verifies user is not a viewer
→ Room `Y.Doc` updates and broadcasts delta to other connected clients
→ `scheduleSave()` in `collaborationserver/src/persistence.js` buffers save (3.5s quiet period)
→ REST PATCH writes snapshot to Firestore `workspaces/{id}/files/{fileId}`.

### D. Code Execution Flow
User clicks "Run" in `<Output />`
→ `executeCode()` in `src/api.js` retrieves Firebase ID token
→ `POST /api/workspace/[workspaceId]/execute`
→ `authenticateAndAuthorizeExecution()` in `src/lib/execution/executionAuth.js` checks role (Viewers blocked)
→ `ExecutionService.execute()` acquires concurrency slot
→ `SandboxExecutor.execute()` writes files to temporary scratch folder `data/executions/{id}`
→ Spawns Docker container using image from `RuntimeRegistry` with isolation flags
→ Returns `{ stdout, stderr, exitCode, status }` and destroys scratch container.

### E. AI Agent Code Modification Flow
User inputs task prompt into `<AgentPanel />`
→ `runAIAgent()` in `src/api.js`
→ `POST /api/workspace/[workspaceId]/agent`
→ `verifyAIWorkspaceAccess()` checks caller membership and sliding rate limit
→ `AgentOrchestrator.run()` initializes run and baselines files via `SafeRollbackService`
→ `geminiProvider.js` sends prompt and tool definitions to Google Gemini
→ Gemini issues `apply_patch` tool call
→ `src/lib/ai/tools/registry.js` executes patch on disk
→ `firestoreSync.notifyCollabMutation()` sends `/notify-mutation` to collaboration server
→ Live Monaco editor reflects changes; response and run ID returned to user.

## 16. Core Architecture Invariants

1. **Client Never Bypasses Authorization**: Frontend role checks improve user experience; server-side routes enforce security boundaries unconditionally.
2. **Server-Enforced RBAC**: Every backend endpoint independently validates workspace membership and permissions.
3. **Yjs is the Single Real-Time Protocol**: All live editor syncing occurs via Yjs CRDTs over WebSocket. Firestore is used for snapshots, not real-time polling.
4. **Docker is the Sole Execution Sandbox**: Code execution runs strictly inside container sandboxes. No host or remote third-party execution (Piston) is permitted.
5. **No Client-Controlled Containers**: The client cannot specify arbitrary Docker container images, shell commands, or runner binaries.
6. **AI Credentials Remain Server-Side**: Gemini API keys are accessible only in server environments and are never inlined into client bundles.
7. **Workspace Isolation**: Git repositories and execution scratch spaces are strictly namespaced by workspace ID to prevent cross-tenant data leaks.
8. **No Redundant Databases**: Firestore is the document database; Realtime Database is used strictly for live presence cursors.
9. **Single Authentication Architecture**: Firebase Auth handles user identity; Next.js verifies ID tokens via the official Google Identity Toolkit REST API.
10. **Unified Toast Notifications**: All client notifications use `react-toastify`.
11. **Modular Service Boundaries**: Domain logic is grouped by directory (`execution/`, `git/`, `ai/`) with dedicated error classes.
12. **Stable UI Contracts**: Existing UI components and layout structures adhere to the design system and avoid styling churn.
